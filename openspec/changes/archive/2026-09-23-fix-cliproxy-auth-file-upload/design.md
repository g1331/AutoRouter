## Context

问题证据见 proposal.md。上游 v7.3.12 的 JSON 上传分支先读取查询参数 `name`，缺少时返回 `400 invalid name`。现有前端读取文件名仅用于展示，未进入请求链路。

## Goals / Non-Goals

目标是修复命名契约并保持原有 JSON body 兼容。不会转换认证内容、更改下载删除语义或增加新的 UI 控件。

## Decisions

- 使用可选 `name` 查询参数，避免把认证 JSON 包装成新结构而破坏旧调用方。文件名在路由边界校验，在上游请求中 URL 编码。
- 无文件名时在服务端生成 `auth-<UUID>.json`，避免固定默认名覆盖其他账号；有文件名时保留用户选择的名字及上游同名行为。
- 移除部署命令的 `--remove-orphans`；主应用工作流无法从主 Compose 判断可选 sidecar 是否应删除。

```text
上传弹窗（既有标题与说明）
  [选择文件] [粘贴 JSON]
  文件名展示 / JSON 输入框
  [取消] [上传]
       ↓ 内容 + 可选文件名
Admin API → 名称校验 / 唯一名称生成 → 上游 ?name=编码名称 → 账号同步
```

界面布局和视觉层级不变；只调整提交数据，不添加额外输入步骤。

## Risks / Trade-offs

- 相同显式文件名沿用上游覆盖语义 → 本次不扩展冲突交互；粘贴使用唯一名称。
- 上游成功但同步失败仍可能返回错误 → 保持现有语义，本次聚焦可复现的缺少文件名问题。
- 真实凭据内容是否被上游支持不属于命名契约 → 使用隔离实例和无敏感信息的 fixture 验证上传协议，不使用用户截图凭据。

## Migration Plan

无需数据库迁移。PR 合并后基于合并提交发布下一个 beta，并运行 Personal Deploy；部署前保留 Compose、环境文件及数据库备份，部署后确认版本、sidecar 和鉴权。回滚可部署此前的发布镜像。
